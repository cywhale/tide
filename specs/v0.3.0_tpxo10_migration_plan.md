This plan upgrades the ODB Tide API data source from TPXO9-atlas-v5 to
TPXO10-atlas-v2 and replaces the legacy conversion pipeline
(`dev/extract_parallel.py` + `dev/zarr_fillna_*.py`) with a single
deterministic, lossless, test-gated pipeline. It deliberately separates the
**data-layer migration** (this spec) from any later **runtime performance
work** (deferred to v0.3.x follow-ups), mirroring the staged approach used in
`~/proj/gebco` for the GEBCO_2023 → GEBCO_2026 migration.

---

## 1. Goals / Non-Goals

Goals:

1. Produce `data/tpxo10.zarr` from `data_src/TPXO10_atlas_v2/` via a
   **one-pass pipeline with two precisely separated logical layers** (see
   §3.0 for the binding definition): a bit-exact *source layer* repack plus
   a deterministic, flag-delimited *derived fill layer*. No global
   pre-interpolation, no post-hoc fill scripts, fully re-runnable with
   deterministic output.
2. Store harmonic constants on their **native Arakawa C-grid nodes**
   (z / u / v each with their own coordinates) plus `hz/hu/hv` bathymetry,
   so transport→velocity conversion and coastal phase fidelity no longer
   depend on cross-node interpolation done at conversion time.
3. Keep the runtime query path architecturally unchanged:
   pure Zarr indexing + harmonic synthesis. **Runtime stays on pyTMD 2.2.8**;
   pyTMD 3.x is used only inside the conversion environment. The Zarr store
   is the contract boundary between the two.
4. Migrate project tooling to `uv` (production env + a separate conversion
   env), retiring pyenv/Pipfile.
5. Gate every stage with explicit, reproducible tests: unit tests,
   NetCDF↔Zarr consistency, TPXO9↔TPXO10 cross-version consistency
   (tolerance-based), golden-value checks against direct pyTMD computation,
   observation validation (NOAA/CWA), and performance non-regression
   benchmarks.

Non-goals (deferred):

* No FastAPI feature work or endpoint redesign (only the minimal
  `src/model_utils.py` / `tide_app.py` changes needed to read the new store).
* No runtime migration to pyTMD 3.x in v0.3.0. It may be evaluated later as
  an isolated experiment behind the same benchmark gates (§7.6).
* No change to `/api/tide/forecast` semantics beyond the reference string
  (`TPXO9_atlas_v5 …` → `TPXO10_atlas_v2 …`).
* No VM deployment work in this spec (cutover checklist is a follow-up,
  modeled on `gebco/specs/vm37_pre_cutover_checklist.md`).

## 2. Verified facts (basis for the design — all checked on 2026-06-11)

These were verified directly against local files and an installed
pyTMD 3.0.6, not taken from secondary sources:

* **TPXO10-atlas-v2 NetCDF is schema-identical to TPXO9-atlas-v5.**
  `data_src/TPXO10_atlas_v2/` contains 31 files
  (`grid_tpxo10atlas_v2.nc` + 15 `h_*` + 15 `u_*`), dims `nx=10800, ny=5401`
  (1/30°), same variable names/dtypes/units as TPXO9:
  - grid: `lon_z/lat_z/lon_u/lat_u/lon_v/lat_v` (float64),
    `hz/hu/hv` (float32, meters) — bathymetry at *all three* node types.
  - `h_<con>`: `hRe/hIm` int32, **millimeter**, on z-nodes.
  - `u_<con>`: `uRe/uIm/vRe/vIm` int32, **centimeter²/sec** (transport),
    on u/v-nodes.
  - Same 15 constituents as TPXO9-atlas-v5:
    `2n2, k1, k2, m2, m4, mf, mm, mn4, ms4, n2, o1, p1, q1, s1, s2`.
  - Sanity: M2 at (119.5°E, 24.5°N) |hc| ≈ 1.84 m (Taiwan Strait, plausible);
    `hz/hu/hv` ≈ 65/64/62 m at the same index.
* **What actually changed in TPXO10** is data quality, not format: bathymetry
  and coastlines are *independently defined* at u/v nodes (not derived from
  z), ~2× assimilated altimetry, Cryosat-2 in polar regions.
* **pyTMD 3.0.6** opens these files directly:
  `pyTMD.io.ATLAS.open_atlas_dataset(file, group=...)` returns an xarray
  Dataset with complex constituent variables. **Correction (review round
  9, verified empirically during T-D1)**: although the docstring labels
  `group='u'` as currents, at the `open_atlas_dataset` layer the returned
  values are *transport* in cm²/s (units attr `centimeter^2/sec`); the
  depth division happens in higher-level accessors. The grid reader
  (`open_atlas_grid(group=...)`) returns per-node `bathymetry` with land
  masked to NaN (the store keeps the raw 0). The model database includes
  `TPXO10-atlas-v2-nc` with exactly the file names we downloaded.
* **pyTMD 3.x is a breaking rewrite**: `ATLAS.extract_constants` is gone;
  `predict.time_series` / `predict.infer_minor` changed signature to
  `(t, ds: xr.Dataset)`. This is why the runtime stays on 2.2.8 in v0.3.0.
* **Root cause of the legacy missing-data pain**: the old pipeline
  interpolated all variables onto the z-grid at conversion time with
  `extract_constants(..., method='spline')` and no extrapolation; masked
  points became NaN (~204,969 points), requiring the
  `zarr_fillna_*` re-extraction scripts. Storing native nodes losslessly
  removes this failure class by construction.

## 3. Key decisions

### 3.0 Terminology (binding): "lossless" and the two logical layers

The store is **not** a byte-for-byte mirror of the source; it is the union
of two logical layers, discriminated cell-by-cell by the `*_flag`
variables, and every claim of "lossless"/"exact" in this spec is scoped by
flag value:

* **Source layer (`flag == 0`)**: cells valid in the source per §3.2. Their
  `Re/Im` int32 values are **bit-exact copies** of the source NetCDF (after
  the §3.1 index transpose). "Lossless" in this spec means *exactly this
  layer and nothing more*. The T-B gate demands tolerance-0 equality here.
* **Derived fill layer (`flag == 1`)**: cells invalid in the source, filled
  by one deterministic inpaint pass (pinned algorithm + parameters recorded
  in store attrs, D8). These are *derived* values; T-B verifies only that
  (a) the source cell was indeed invalid and (b) the stored value is
  finite and reproducible (same pipeline run ⇒ same bytes).
  **Quantization rule (binding — review round 6 finding 1; order pinned
  per round 7 finding 2)**: inpaint operates on `Re` and `Im`
  independently in float64; write-back proceeds in exactly this order:
  (1) `rounded = np.rint(value)` (ties-to-even), (2) check `rounded` is
  finite and within int32 range, (3) cast to int32. The check applies to
  the *rounded* value, so inputs near the int32 boundary that round to a
  representable integer pass uniformly across implementations. Any
  non-finite or out-of-range `rounded` aborts the pipeline with a
  diagnostic (silent clipping/wrapping is forbidden; such a value
  indicates an inpaint bug, not data to be salvaged). The rounding rule
  and a quantization-rule version string go into the store attrs.
* **Invalid layer (`flag == 2`)**: land/permanently-invalid cells, stored
  as int 0/0.

Implementation consequence: the fill is written into the same `Re/Im`
arrays (not separate variables) **only because** `flag` makes the layers
recoverable at any time: `source = Re/Im where flag==0`. Any code or test
that needs "the lossless data" must mask by `flag == 0`; any wording
elsewhere in this spec that says "lossless repack" means the source layer
under this definition.

| D12 | **API output grid stays the z-grid; u/v are centered onto z-nodes at conversion time** as a derived layer (`uz_Re/uz_Im/vz_Re/vz_Im`, float32 complex parts, units m/s, own `uz_flag/vz_flag`). Centering algorithm (binding, index-explicit on the stored `(lat, lon)` axis order, `j` = lat index ∈ [0, ny), `i` = lon index ∈ [0, nx), per constituent): edge velocities first — `eu[j,i] = 1e-4·(u_Re[j,i] + 1j·u_Im[j,i]) / hu[j,i]` over valid u-edges, `ev` analogous with `hv`. Then **u centers along longitude with periodic wrap** (the grid is global 0–360°): `uz[j,i] = 0.5·(eu[j,i] + eu[j,(i+1) mod nx])`. **v centers along latitude, non-periodic**: `vz[j,i] = 0.5·(ev[j,i] + ev[j+1,i])` for `j+1 < ny`; at the last latitude row (`j = ny−1`) only the southern edge exists → one-sided. Validity case analysis (per cell, per component, **flag precedence over inpainted inputs included** — review round 4, finding 2): flag 0 ⇔ both edges usable **and** both have native `u_flag/v_flag == 0`; flag 1 ⇔ one-sided (incl. the lat-boundary row) **or** any used edge is inpainted (`flag == 1`); flag 2 ⇔ no usable edge (value 0). **Regional conversion rule (review round 4, finding 1)**: the longitude modulo wrap is valid **only** for the full global grid; a `--region` run must read a **halo** from the global source beyond the output region — ≥1 extra column east and ≥1 extra row north for centering, plus the inpaint method's `radius × iterations` extent for inpaint — compute on the haloed arrays, then write only the output region; local wrap at a regional boundary is forbidden (a 150°E edge must never borrow 105°E data), and cells whose halo lies outside the fetched source are flagged per the one-sided/invalid rules only if the *global* source itself ends there (never at an artificial regional edge). **Node-offset convention is asserted, not assumed**: Stage 0 `inspect_source.py` must verify from the grid file that `lon_u = lon_z − Δ/2` (u on the western cell edge) and `lat_v = lat_z − Δ/2` (v on the southern edge), Δ = 1/30°; if the source convention differs, the neighbor index in the formulas flips and this row is amended before Stage 1. | Resolves the C-grid↔API-contract alignment (review round 2 finding 2; round 3 finding 3 pinned axis order, the 0°/360° periodic wrap for `uz`, the non-periodic latitude boundary for `vz`, and made the edge-offset convention a Stage 0 assertion) without any of the three failure modes: response coordinates and values stay consistent (one grid), the runtime does **zero** regridding/nearest search per request, and bbox queries remain contiguous slices on one grid. Edge-velocity averaging (divide by edge depth `hu/hv` first, then average) is the standard C-grid centering and preserves pyTMD's per-edge transport→velocity convention; deterministic, mask-aware, flag-audited, golden-tested (§7.4 incl. dateline wrap column, first/last lon columns, latitude-boundary rows, polar cells). |

### 3.1 Target Zarr schema

```
data/tpxo10.zarr  (zarr v2, consolidated)
├── coords: lon_z(10800) lat_z(5401) lon_u(10800) lat_u(5401)
│           lon_v(10800) lat_v(5401) constituents(15, <U3)
│
│  -- truth layers (source repack per §3.0; runtime does NOT read u/v natives) --
├── z_Re, z_Im   int32  (lat_z, lon_z, constituents)  units: mm
├── u_Re, u_Im   int32  (lat_u, lon_u, constituents)  units: cm^2/s (transport)
├── v_Re, v_Im   int32  (lat_v, lon_v, constituents)  units: cm^2/s (transport)
├── hz           float32 (lat_z, lon_z)  units: m
├── hu           float32 (lat_u, lon_u)  units: m
├── hv           float32 (lat_v, lon_v)  units: m
├── z_flag       uint8  (lat_z, lon_z)   0 source / 1 inpainted / 2 invalid
├── u_flag, v_flag                        (same semantics, per node type)
│
│  -- derived layer (D12 conversion-time C-grid centering; runtime-facing) --
├── uz_Re, uz_Im float32 (lat_z, lon_z, constituents)  units: m/s
├── vz_Re, vz_Im float32 (lat_z, lon_z, constituents)  units: m/s
├── uz_flag, vz_flag uint8 (lat_z, lon_z)  0 both edges native (u/v_flag==0)
│                                          1 one-sided OR any edge inpainted
│                                          2 no usable edge (D12 precedence)
│
│  -- optional overview (last-resort, owner sign-off required; see note) --
├── overview5/   stride-5 exact decimation of runtime-facing vars
│
└── attrs: tide_store_schema = "tpxo10-cgrid-v1" (D9 adapter key);
       provenance per D8; unit-conversion constants documented:
       z:  hc[m]    = 1e-3 · (z_Re + 1j·z_Im)
       u:  U[m^2/s] = 1e-4 · (u_Re + 1j·u_Im);  u[m/s] = U / hu  (per edge)
       uz/vz: already velocity, D12 centering — no runtime conversion
```

Runtime read set is exactly: `z_Re/z_Im`, `uz_*`, `vz_*`, coords,
`tide_store_schema` (+ `overview5/` if adopted). Native u/v nodes, `hz/hu/hv`
and flags are archive/audit/conversion-input only.

Overview contingency — **demoted to last resort** (review round 3,
finding 1): the legacy sampling semantic is *phase-dependent* — the API
slices the bbox first and decimates from the bbox's first index
(`tide_app.py:374-378`), so the sampled grid shifts with the bbox origin.
A single global stride-5 decimation preserves only phase (0,0); serving it
for arbitrary bboxes **changes returned coordinates and values**, i.e. it
is an API-visible behavior change in D11's sense. Full phase compatibility
would need 25 `(lat_phase, lon_phase)` copies (~+100% store size) — not
acceptable. Note also the I/O ceiling: with chunk width ≫ stride, a
`sample=5` bbox touches every underlying chunk regardless, so an overview
only reduces decompressed bytes, never chunks touched. Therefore:
`overview5/` may be adopted **only if** (a) the §7.5 large-map gates fail
for every cell of the chunk matrix, **and** (b) the owner explicitly signs
off the sampling-grid semantic change, with G1 evidence comparing overview
vs legacy selection coordinates *and* values side by side. Default: not
built.

Note on transposition: source NetCDF is `(nx, ny)`; the store is written
`(lat, lon, constituents)` to match the runtime access pattern (same
orientation as the current `tpxo9.zarr`). The transpose is part of the
lossless repack and covered by the equality gate (§7.2 compares
index-mapped values, not raw byte order).

### 3.2 Validity mask definition (to be pinned in Stage 1)

Provisional rule: a node is *valid source* iff its bathymetry (`hz`/`hu`/`hv`
respectively) > 0 **and** not all 15 constituents are (0+0j). The prototype
must verify this rule against pyTMD 3.x's own mask logic and against the
TPXO9 store's known-good coverage; the final rule is frozen in this spec
before Stage 2 (update this section, do not leave it implicit in code).

### Stage 1 — Prototype + calibration (regional, throwaway store)

> **G1 kickoff confirmation (owner sign-off, 2026-06-11)** — conversion
> contract and absolute thresholds frozen as: quantization
> `np.rint → rounded finite/range check → int32 cast`; **no depth clamp**
> by default, `h ≤ 0` ⇒ invalid, edge-depth/outlier survey first;
> Gunicorn worker delta ≤ 1.5 GiB / peak ≤ 2 GiB (safety budget,
> instrumentation-enforced); Dask worker delta ≤ 2 GiB / peak ≤ 4 GiB;
> aggregate tree delta ≤ 3 GiB / host-RAM headroom ≥ 25%; payload ≤
> 100 MiB; latency ≤ 15 s single / ≤ 30 s concurrency-2; W8 launched
> production-like **without `--reload`**.
> **Stop conditions**: if the edge-depth survey shows a clamp is needed,
> or any W8 threshold fails, work STOPS at G1 for re-sign-off of the
> policy — thresholds must not be adjusted unilaterally and no canonical
> data may be written.

Deliverables:
* `dev_tpxo10/scripts/convert_to_zarr.py --region lon0,lon1,lat0,lat1`
  producing a regional prototype store with the full §3.1 schema.
  **Output region: 104–151°E, −1–46°N; benchmark area: 105–150°E,
  0–45°N** (real source data, single contiguous conversion). The output
  region is deliberately one degree larger on every side than the

  finding 1). All §7.5 bboxes run against *real* data, never synthetic

  ratio, page-cache behavior, chunk reuse and cold I/O, and are

  the Taiwan Strait shallow/strong-current cells, Kuroshio, coastal
  one-sided centering cases, and open Pacific.
  Runtime-facing variables for this region are ≈1 GB raw — conversion
  remains a minutes-scale, repeatable run per chunk-matrix candidate.
  **Halo handling (D12 regional rule)**: the converter reads the source
  with a halo beyond 104–151°E / −1–46°N (≥1 cell for centering; inpaint
  radius × iterations for inpaint), computes on the haloed arrays, writes
  only the output region, and never wraps at regional edges. All §7.5
  benchmark bboxes lie within the 105–150°E / 0–45°N benchmark area,
  strictly inside the output region; `convert_to_zarr.py` records the
  output-region bounds in the store attrs so the benchmark scripts can
  assert containment rather than trust convention.

### 7.2 T-B: NetCDF ↔ Zarr consistency (lossless gate)

Script: `dev_tpxo10/scripts/verify_against_netcdf.py`.

* Opens source NetCDF and `tpxo10.zarr` with `decode_cf=False`; compares
  via index mapping (§3.1 transpose).
* **Where `*_flag == 0`: exact integer equality, tolerance 0**, for all six
  Re/Im variables × 15 constituents.
* Where `*_flag == 1` (inpainted): assert source value was *invalid* per
  §3.2 (i.e., inpaint only ever fills invalid cells) and stored value is
  finite.
* Where `*_flag == 2`: stored value is exactly (0+0j) ints.
* Coordinates (`lon_*`, `lat_*`): full-scan float64 exact equality.
* `hz/hu/hv`: full-scan float32 exact equality.
* Derived layer (D12): `uz/vz` recomputed by an **independent
  reimplementation** of the centering rule (test code, not the pipeline's
  function) from the stored native `u/v` truth layers; match within
  rtol ≤ 1e-6 (float32 op-order budget); `uz_flag/vz_flag` exact match
  against the rule's case analysis (two-edge / one-sided / invalid).
* Modes: `--sample` (default; ≥100k points/var, 10 seeded rounds, window
  sampling) and `--full` (one full scan required before G2 sign-off).

Pass: zero mismatches. Any mismatch fails the stage — no tolerance creep on
this gate; it is the foundation that makes every later error attributable.

### 7.3 T-C: TPXO9-zarr ↔ TPXO10-zarr cross-version consistency

Script: `dev_tpxo10/scripts/compare_tpxo9_tpxo10.py`.

Values *will* differ (different model generations); the gate is that
differences are **bounded, spatially explicable, and unbiased**, with hard
thresholds frozen after Stage 1 calibration.

Method:
* Primary comparison on **z at z-nodes** (both stores share the identical
  1/30° z-grid, so alignment is exact; the old store's amp/ph are converted
  to complex `hc_old`, the new store's Re/Im to `hc_new`).
* Metric per constituent: vector difference `|Δhc| = |hc_new − hc_old|`
  (combines amplitude+phase; immune to 0/360 phase-wrap artifacts).
  Secondary report: amp diff and circular phase diff for interpretability.
* Sampling: ≥100k ocean points common-valid in both stores, stratified:
  50% global uniform, 25% shelf/coastal (h < 200 m), 25% polar (|lat| > 60°
  — Cryosat-2 assimilation region, expected largest legitimate change).
  Seeded, reproducible. Report per-stratum histograms, P50/P75/P90/P95/P99,
  signed mean (bias), and top-20 outliers with coordinates.
* Currents — two distinct comparisons (review round 7, finding 1; the
  runtime-facing layer is D12 `uz/vz` on the z-grid, *not* the native
  nodes):
  - **Runtime-facing `uz/vz` vs the old store's z-grid currents**:
    same-coordinate comparison on the shared z-grid (old legacy-regridded
    values vs new centered values) — report-only diagnostic with the same
    stratified statistics as z; differences mix genuine TPXO10 changes
    with the regridding-method change, so no grid-level gate.
  - **Native u/v truth layers**: data-quality report only (coverage,
    outliers, per-constituent distributions); explicitly *not* a statement
    about API behavior.
  The *binding* current gates remain station-level (T-F: time series &
  tidal ellipse at validation stations).

Provisional pass thresholds (z, per major constituent M2/S2/K1/O1 —
**to be calibrated and frozen at G1**):
* Deep ocean (h ≥ 1000 m): P95 |Δhc| ≤ 30 mm.
* Shelf (200 m > h ≥ 50 m): P95 |Δhc| ≤ 150 mm.
* Coastal (h < 50 m): report-only (genuine model improvement expected to
  dominate; no hard bound), but top outliers must be reviewed and
  explicable (e.g., resolved embayments), not artifacts (stripes, tiles,
  node-offset errors — any spatially structured artifact fails the gate).
* Signed mean amp difference (deep ocean, M2): |bias| ≤ 5 mm
  (catches systematic unit/scale errors — this is the check that would
  have caught the historical `U/(D/100)` class of bugs immediately).
* Minor constituents: report-only with the same structure.

### 7.4 T-D: Golden-value checks against direct pyTMD computation

T-D1 (conversion correctness, Stage 1/2): at ≥200 seeded node indices per
node type (stratified deep/shelf/coastal/polar + 20 fixed named locations
incl. Taiwan Strait, Kuroshio, Gulf of Maine, Weddell Sea). Scope note:
**integer-level exactness is T-B's job and only T-B's** — T-D1 compares
*derived* floating-point quantities across two independent code paths
(our pipeline vs pyTMD 3.0.6), so it uses small numerical tolerances; a
T-D1 deviation beyond tolerance signals a convention bug (units, scale,
node mapping), not byte corruption:
* `hc` from `tpxo10.zarr` (exact node index, units aligned) vs the value
  read by pyTMD 3.0.6 `open_atlas_dataset` at the same node:
  rtol ≤ 1e-9, atol ≤ 1e-9 in the aligned unit (float64 arithmetic on
  identical int32 inputs differing only in conversion order).
* Transport check: store `u_Re/u_Im` and `v_Re/v_Im` ints vs pyTMD 3.0.6
  `open_atlas_dataset(group='u'/'v')` values (transport, cm²/s at this
  layer — see the §2 correction), rtol ≤ 1e-9; `hu/hv` vs
  `open_atlas_grid` per-node bathymetry (land-mask convention: pyTMD NaN
  ↔ store 0), exact on finite cells.
* Centering check (D12, both components): store `uz` AND `vz` vs two-edge
  averages hand-computed from pyTMD-READ transport and pyTMD-READ edge
  depths (the reference never touches store arrays), rtol ≤ 1e-5; must
  include coastal indices exercising the one-sided and invalid branches
  and the halo-dependent boundary cells (easternmost column / northernmost
  row, outer edge read from the global source); dateline wrap column,
  first/last longitude columns, last-latitude row and polar (Arctic) cells
  are exercised by unit tests now and the Stage 2 global golden run.

T-D2 (runtime correctness, Stage 3): predicted hourly series over two fixed
30-day windows (one near solstice, one near equinox, fixed dates) at the 20
named locations:
* Our runtime (pyTMD 2.2.8 `predict.time_series` + `infer_minor` over
  zarr-derived `hc`) vs pyTMD 3.0.6 full-stack prediction from the source
  NetCDF at the same nodes.
* Pass (provisional, freeze at G1): RMSE ≤ 5 mm and max|Δ| ≤ 20 mm per
  station. This cross-checks nodal-correction/minor-inference equivalence
  across the 2.x/3.x boundary — the single most likely place for silent
  numerical drift, hence its own gate.

### 7.5 T-E/T-G: Performance consistency (read speed + API latency)

#### 7.5.0 Query critical-path model (what each design lever controls)

Every request decomposes into five cost terms; the benchmarks below are
designed so each term is observable in isolation, because a wall-clock-only
gate cannot tell which lever to pull when it fails:

1. **Coordinate resolution** — `searchsorted` on eagerly-loaded coordinate
   arrays; O(log n), negligible. Runtime requirement: coords are
   materialized once at startup, never dask-backed.
2. **Chunk I/O (dominant term)** — #chunks touched × (read + blosc
   decompress). Governing metric: *read amplification* = decompressed
   bytes ÷ bytes actually needed. Worst case is the single-point query
   (1 node from an entire chunk); the inverse case is the large bbox
   (per-chunk fixed overhead amortizes, total bytes dominate). Lever: D5
   chunk shape (and the overview5 contingency for sampled maps).
3. **Graph/scheduling overhead** — `chunks='auto'` routes reads through
   dask: per-request graph build + scheduling is a fixed ms-scale tax that
   dominates small queries; large sliced reads can fan out into many tasks.
   Lever: open-mode (dask vs direct `chunks=None` zarr indexing) — in the
   Stage 1 matrix; interaction with the v0.2.8 shared-Dask-service
   architecture must be measured, not assumed.
4. **Harmonic synthesis** — O(points × constituents × timesteps) vectorized
   numpy (`predict.time_series`/`map` + `infer_minor`); unchanged by this
   migration (D6). Not a lever here.
5. **Serialization & memory** — large maps are bounded by JSON size / peak
   RSS, not chunk layout (45°×45° at sample=1 ≈ 1.8M cells × 3 vars).
   Lever: response/cell-count guards (existing truncate mode; cap review in
   P-Map45-s1 below).

#### 7.5.1 Stage 1 chunk/open-mode matrix (blocking at G1)

Script: `dev_tpxo10/scripts/benchmark_chunk_matrix.py`, run on the Stage 1
regional prototype rebuilt per candidate. Full factorial: spatial chunk
{113², 225², 450²} × constituent chunk {5, 15} × open-mode {dask-auto,
direct}. Workloads: W1 point all-15-constituents; W2 point M2-only; W3
point 5-constituent subset; W4 1°×1° map; W5 10°×10° map; W6 45°×45°
map sample=5; W7 45°×5° elongated map; W8 45°×45° map sample=1 (the
§7.5.3 cap-decision workload). W4–W8 run against real source-backed data
inside the 105–150°E / 0–45°N benchmark area of the prototype store
(output region 104–151°E / −1–46°N) — synthetic tiling is inadmissible
(round 3, finding 2). Sampling workloads must exercise at
least two different bbox-origin phases (the legacy decimation is
phase-dependent, §3.1 overview note).

**Blocking instrumentation per cell of the matrix** (review round 2,
finding 6 — wall-clock alone is inadmissible as G1 evidence):
* chunks touched; compressed bytes read; decompressed bytes,
* dask task count (dask mode) / call count (direct mode),
* peak RSS delta,
* cold-cache first-access latency — requires **verifiable page-cache
  eviction**, with the eviction method recorded in TESTING.md (Linux:
  `sync; echo 3 > /proc/sys/vm/drop_caches` or `vmtouch -e <store>`;
  macOS dev box: `purge`). Neither a fresh process nor copying the store
  to a new path qualifies (the copy itself populates the page cache —
  review round 4, finding 4). If eviction is unavailable in an
  environment, that round is labeled `first-path-access` and **cannot**
  serve as the cold-cache evidence; the cold-cache gate must then be run
  on a host where eviction is possible (the production-like Linux VM),
* wall-clock mean/median/P95.

G1 freeze: the winning (chunk, open-mode) pair and the full matrix table go
into this spec; the D5 binding constraint (point-query decompressed bytes ≤
1.5× tpxo9 baseline) must hold for the winner.

Script: `dev_tpxo10/scripts/benchmark_old_new_api.py`. Both stores on the

Patterns (matching real API usage, incl. the documented 45° max bbox):

* P2: single-point 1-day time series, 10-min step (`/api/tide` point path).
* P3: bbox map at one timestamp: 1°×1°, 5°×5°, 10°×10°.
* P-Map45-s5: 45°×45°, `sample=5` (default large map request).
* P-Map45-s1: 45°×45°, `sample=1` — re-confirms on the global store the

* P-Strip: 45°×5° elongated bbox (chunk-alignment pathology check).
* P4: cold-cache first-query latency (page cache dropped, per 7.5.1).

#### 7.5.3 `MAX_BBOX_CELLS` decision procedure (decided at G1)

Whether v0.3.0 introduces a cell-count cap for large unsampled maps is
decided by measurement at G1 — but against **absolute thresholds frozen
here, in advance**, so the decision cannot be fitted to whatever numbers
come out (review round 3). Scale of the hazard: 45°×45° at `sample=1` is
1350² ≈ 1.82M cells; with z+u+v plus coordinates ≈ 9.1M values, ~70 MiB as
raw float64, multiplying through Python lists / JSON encoding /
intermediate copies into potentially hundreds of MiB RSS per request. The
default `sample=5` (~73k cells) is likely the only regime production has
actually exercised.

Procedure (on the Stage 1 real 105–150°E store, winning chunk config):
* Run W8 (45°×45°, `sample=1`, z+u+v) as **a single request and as 2
  concurrent requests** (matching the current Gunicorn worker count), and
  **verify from access logs / instrumentation that the two concurrent
  requests are actually served by two distinct worker PIDs** (a
  single-worker pile-up measures queueing, not concurrency).
* **Memory accounting covers the whole service tree** (review round 4,
  finding 3): in dask mode the payload can simultaneously exist in the
  Dask worker, the Gunicorn worker, and serialization intermediates — and
  the deployment runs a separate 8 GB Dask worker (`conf/simu.sh`) whose
  RSS a PM2 per-process limit does not see. Record per-request peak RSS
  delta for (a) each Gunicorn worker, (b) the Dask worker process(es), and
  (c) the aggregate process tree (pm2/gunicorn/uvicorn/dask children).
* **Memory is gated on four readings per process scope, not delta alone**
  (review round 5, finding 3 — a passing delta on a high baseline can
  still breach the PM2 4 GB restart limit): record baseline RSS (idle,
  post-warmup), absolute peak RSS, request-induced delta, and remaining
  headroom against the governing limit (PM2 restart limit for Gunicorn
  workers; the 8 GB allocation for the Dask worker; host RAM for the
  aggregate tree).
* **Supervision-topology note (review round 8, finding 3)**: PM2's
  `max_memory_restart` governs the *supervised shell script*
  (`conf/ecosystem.config.js` → `start_app.sh`), **not** the Gunicorn
  worker children — so no per-worker limit is actually enforced by PM2
  today. The Gunicorn peak threshold below is therefore a **project
  safety budget enforced by the W8 worker-PID instrumentation gate**, not
  a claim about runtime supervision. (Making PM2 — or Gunicorn flags —
  truly enforce a per-worker limit is a deployment follow-up, out of
  v0.3.0 scope.) W8 benchmark runs must launch Gunicorn **without
  `--reload`** (the reloader perturbs both memory and latency).
* Frozen absolute thresholds (provisional values; freeze final numbers at
  G1 kickoff *before* running, recorded in this spec):
  - per Gunicorn worker: delta ≤ 1.5 GiB **and** absolute peak ≤ 2 GiB
    (safety budget, instrumentation-enforced per the note above),
  - Dask worker (dask mode only): delta ≤ 2 GiB **and** absolute peak ≤
    4 GiB (50% of its 8 GB `--memory-limit` allocation),
  - aggregate process-tree: delta ≤ 3 GiB at concurrency 2 **and**
    absolute peak leaves ≥ 25% host-RAM headroom,
  - response payload ≤ 100 MiB,
  - wall-clock ≤ 15 s single / ≤ 30 s at concurrency 2.
* If **all** thresholds hold: v0.3.0 keeps the uncapped legacy behavior —
  no API-visible change (owner preference, D11 spirit).
* If **any** threshold is exceeded: introduce `MAX_BBOX_CELLS`, counted on
  **output cells after `sample` is applied** (`ceil(nlat/sample) ·
  ceil(nlon/sample)` per the §3.1 phase-dependent decimation), *not* on
  raw bbox area — so default `sample=5` requests at 45° stay unaffected
  and only genuinely oversized outputs are rejected (HTTP 4xx with a
  descriptive message). Cap value derived from the measured
  threshold-crossing point, env-overrideable, documented in change_log as
  a protective limit. Owner sign-off required either way (it is an
  API-visible change when triggered).

### 7.6 T-F: Observation validation (accuracy must not regress)

* Re-run `test/compare_observ_tide01.py` (NOAA stations) and
  `examples/case1_cwa_odb_pytmd_compare.py` (CWA Taiwan stations) against
  both old and new APIs.
* Pass criterion: per-station RMSE vs observations — TPXO10 ≤ TPXO9 + 1 cm
  at ≥ 80% of stations, and mean RMSE across stations strictly ≤ TPXO9's.
  Stations where TPXO10 is worse by > 3 cm are individually investigated

* Current validation: tidal-ellipse parameters (`src/pytmd_utils.py

## 8. Risks

| Risk | Mitigation |
|------|------------|
| pyTMD 3.0.x is young (xarray rewrite, months old) | Used only in the conversion env, pinned ==3.0.6; T-D golden gates cross-check it against 2.2.8 numerics; upstream issues localized to conversion, never production. |
| Nodal-correction / infer_minor drift between 2.2.8 and 3.0.6 | T-D2 is a dedicated blocking gate (5 mm RMSE budget). |
| Mask/inpaint rule subtly wrong at coast | §3.2 frozen via prototype evidence; T-B asserts inpaint only touches invalid cells; T-C outlier review catches structured artifacts; flags make every filled cell auditable forever. |
| Transport→velocity convention mismatch (historical bug class) | T-D1 velocity golden check vs pyTMD 3.x `group='u'`; T-C signed-bias gate; unit tests on constants. |
| Chunking choice hurts point or bbox queries (read amplification vs per-chunk overhead pull in opposite directions) | §7.5.1 blocking matrix with I/O instrumentation before the global run; D5 read-amplification ceiling; P3/P-Map45/P-Strip benchmarks at G3; overview5 contingency for sampled maps. |
| Derived `uz/vz` centering convention wrong (velocity-then-average vs average-then-divide, edge cases at coast) | D12 pins the rule incl. one-sided/invalid branches; T-B independent-reimplementation check; T-D1 centering golden test vs pyTMD per-edge currents incl. coastal indices; T-F station validation as the end-to-end accuracy check. |
| u/v node offset breaks an existing API consumer assumption (values shift by ≤ half cell near coast) | Documented in change_log + API reference string bump; T-F station-level validation is the user-facing accuracy check. |
| zarr v2 / numcodecs pinning drift (cf. v0.2.6 numcodecs#721 issue) | Both envs pin zarr/numcodecs exactly; store written and read with the pinned pair; cold-start benchmark (P4) catches metadata-layer surprises. |
| Conversion runtime/memory blowup | Pure repack is I/O-bound streaming via dask; no global interpolation step exists; regional `--region` mode allows incremental burn-in. |

## 9. Open questions and review resolutions

Resolved in review round 1 (Codex review + owner decisions, 2026-06-11):

* **"Lossless" ambiguity (Codex finding 1, High)**: resolved by the binding
  two-layer definition in §3.0; D1/D3/T-B now scope every exactness claim
  by `flag` value.
* **T-D1 over-strict exactness (Codex finding 2, Medium)**: resolved —
  integer exactness lives only in T-B; T-D1 derived comparisons use
  rtol ≤ 1e-9 (hc) / 1e-5 (velocity).
* **Hardcoded store paths outside the spec'd scope (Codex finding 3,
  Medium)**: resolved — Stage 3 now carries an audited path inventory, a
  shared `get_zarr_path()` helper, archival of the legacy fillna test, and
  a repo-wide grep gate.
* **Inpainted values in API responses (was Q4)**: serve transparently, no
  response change — owner decision, now D11.
* **Migrate `test/` validation entrypoints to `TIDE_ZARR_PATH` (Codex open
  question 2)**: yes — owner-approved, covered by the Stage 3 path audit.

Resolved in review round 2 (Codex performance/architecture review,
2026-06-11):

* **Rollback not viable across schemas (finding 1, High)**: resolved — D9
  now specifies a schema-keyed store adapter (`tide_store_schema` attr);
  G3 carries an explicit rollback-proof gate; DoD updated.
* **C-grid ↔ API output contract undefined (finding 2, High)**: resolved —
  D12 binds the API output grid to the z-grid with conversion-time
  C-grid centering (`uz/vz` derived layer, mask-aware two-edge/one-sided
  rule, flags); runtime does zero per-request regridding; native nodes
  remain the stored truth layer. Verified by new T-B derived-layer and
  T-D1 centering checks.
* **Chunk read-amplification & wrong workload assumption (findings 3–4,
  High)**: resolved — D5 no longer asserts a winner; provisional default
  (113,113,15) int32 justified by byte-parity with the production chunk,
  decided by the §7.5.1 blocking matrix (spatial × constituent-chunk ×
  open-mode, incl. constituent-subset workloads), with a hard
  read-amplification ceiling (≤1.5× tpxo9 baseline for point queries).
* **Large/elongated bbox + sampling I/O (finding 5, Medium)**: resolved —
  §7.5.2 adds P-Map45-s5 / P-Map45-s1 (RSS + response-size guard) /
  P-Strip patterns; overview5 exact-decimation contingency specified in
  §3.1 with a G1 go/no-go.
* **Warm-cache benchmarks hide I/O cost (finding 6, Medium)**: resolved —
  chunks-touched / compressed+decompressed bytes / task count / peak RSS /
  cold-cache (page-cache-evicted) latency are blocking instrumentation at
  G1 and required reporting at G3.

Resolved in review round 3 (Codex review, 2026-06-11):

* **overview5 breaks phase-dependent sampling semantics (finding 1,
  High)**: resolved — demoted to last resort in §3.1 (default not built);
  adoption requires failed matrix + side-by-side semantic evidence +
  explicit owner sign-off; the 25-phase full-compatibility option (+100%
  size) documented and rejected.
* **Synthetic 45° tiling inadmissible (finding 2, High)**: resolved —
  Stage 1 prototype region expanded to real 105–150°E / 0–45°N so all
  large-bbox workloads (W4–W8, P-Map45, P-Strip) run on genuine
  source-backed data.
* **D12 boundary conventions undefined (finding 3, Medium)**: resolved —
  index-explicit formulas with periodic lon wrap for `uz`, non-periodic
  one-sided lat boundary for `vz`; node-offset convention asserted by
  Stage 0 `inspect_source.py`; golden/unit tests extended to dateline,
  first/last columns, boundary rows, polar cells.
* **Adapter laziness unspecified (finding 4, Medium)**: resolved — D9 now
  carries a selection-before-materialization contract (eager whole-store
  conversion forbidden), enforced by an instrumented-store unit test.
* **`MAX_BBOX_CELLS` timing and criteria**: moved to a G1 decision
  (§7.5.3) with pre-frozen absolute thresholds (RSS / payload / latency),
  single + concurrency-2 runs, and an output-cells-after-sample cap basis;
  uncapped legacy behavior is kept if all thresholds hold.

Resolved in review round 4 (Codex review, 2026-06-11):

* **Regional prototype lacked halo semantics (finding 1, High)**: resolved
  — D12 regional conversion rule: halo read from the global source
  (≥1 cell for centering; inpaint radius × iterations for inpaint),
  compute-on-halo / write-interior-only, local wrap at regional edges
  forbidden; Stage 1 requires benchmark bboxes inside the halo-clean
  interior, asserted via interior bounds recorded in store attrs.
* **`uz/vz` flag precedence contradiction (finding 2, Medium)**: resolved —
  flag 0 requires both edges native (`u/v_flag == 0`); any inpainted input
  edge ⇒ flag 1; §3.1 schema comment aligned; unit test added.
* **Cap memory accounting incomplete (finding 3, Medium)**: resolved —
  §7.5.3 records per-Gunicorn-worker, Dask-worker, and aggregate
  process-tree RSS (deployment runs a separate 8 GB Dask worker,
  `conf/simu.sh`); added Dask (2 GiB) and aggregate (3 GiB) provisional
  thresholds; concurrency-2 must be verified to hit two distinct worker
  PIDs.
* **Store-copy is not cold cache (finding 4, Medium)**: resolved — §7.5.1
  requires verifiable page-cache eviction with the method recorded;
  otherwise the round is labeled `first-path-access` and the cold-cache
  gate moves to a host where eviction is possible.
* **Adapter schema detection fail-closed (finding 5, Low)**: resolved —
  D9: missing attr ⇒ legacy only with the full legacy variable set
  present; unknown attr or incomplete variables abort startup.

Resolved in review round 5 (Codex review, 2026-06-11 — reviewer also

TPXO10 NetCDF: `lon_u − lon_z = −1/60°`, `lat_v − lat_z = −1/60°`):

* **45° bbox cannot fit strictly inside a 45° region (finding 1, Medium)**:
